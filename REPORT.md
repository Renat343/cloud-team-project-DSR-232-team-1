## 4. Архитектурные компоненты

| Компонент | Назначение и связь с остальными |
| --- | --- |
| Браузер | Клиент пользователя: запрашивает страницы GitHub по HTTPS и отображает каталог |
| GitHub | Облачная платформа: хранит версии файлов, отображает Markdown и обслуживает Pull Requests |
| Markdown-файлы | Данные каталога: описания моделей в `docs/`, примеры сервисов в `examples/`; читаются платформой GitHub |
| Git и локальная копия | Средства редактирования: получают файлы из GitHub и передают изменения в отдельную ветвь |

При чтении браузер обращается к GitHub, платформа получает документы выбранной
ветви и показывает пользователю оформленную страницу. При обновлении участник
редактирует файлы, создаёт commit, отправляет ветвь и открывает Pull Request.
Объединение после проверки переносит изменения в основную ветвь.

Собственного сервера и базы данных у прототипа нет: роль хранилища каталога
выполняют версионируемые текстовые документы.

## 5. Использованные элементы Markdown

| Элемент | Пример из README | Назначение |
| --- | --- | --- |
| Заголовки | `## Архитектура` | Иерархия разделов |
| Маркированный список | Список ограничений | Перечисление свойств и правил |
| Нумерованный список | Шаги просмотра и клонирования | Задание порядка действий |
| Таблицы | Архитектура, технологии, команда | Сопоставление объектов и назначений |
| Ссылки | Переход к описанию моделей | Навигация по репозиторию |
| Полужирное выделение | `**Предварительные условия:**` | Акцент на важных условиях |
| Встроенный код | `git --version` | Выделение команды в тексте |
| Блоки кода | Блоки с языками `bash` и `text` | Команды, дерево каталогов и схемы |

Использовано восемь элементов Markdown, что превышает требуемый минимум из четырёх.

## 7. Ответы на контрольные вопросы

### 1. Для чего файл README.md используется в GitHub-репозитории?

README является точкой входа в проект. Он объясняет назначение, архитектуру,
состав файлов, порядок начала работы, используемые технологии и роли участников.
GitHub отображает его на странице репозитория.

### 2. Какие элементы Markdown позволяют структурировать техническую документацию?

Заголовки задают иерархию; списки описывают состав и последовательность действий;
таблицы сопоставляют характеристики; ссылки связывают документы; выделение
акцентирует важное, а кодовые блоки сохраняют формат команд и примеров.

### 3. Какие сведения необходимо включить в инструкцию по запуску облачного проекта?

Нужно указать предварительные условия, необходимые инструменты и зависимости,
порядок получения проекта, рабочую директорию и ветвь, команды настройки и запуска,
способ доступа к результату и признаки успешной работы. Для данного каталога
достаточно браузера либо Git и редактора с предпросмотром Markdown.

### 4. Почему реальные пароли, токены и ключи доступа нельзя размещать в README и других файлах?

Их раскрытие может дать посторонним доступ к данным и ресурсам.
Удаление секрета из текущего файла не удаляет его из истории Git и чужих копий.
При утечке секрет необходимо отозвать или заменить; приложения должны получать
секреты через предназначенные для этого защищённые механизмы.

### 5. Как качественная документация упрощает командную разработку и сопровождение?

Она сокращает время знакомства с проектом, фиксирует архитектуру и обязанности,
делает действия воспроизводимыми и облегчает проверку изменений.
Участники меньше зависят от устных пояснений и быстрее находят нужные файлы.

## 8. Вывод

Документация делает облачный проект понятным для нового участника:
README связывает назначение, компоненты, данные и порядок работы в единое описание.
Markdown позволяет хранить документацию рядом с материалами проекта и проверять
её изменения через Git и Pull Requests. Актуализация README при изменении структуры
или способов запуска снижает ошибки при сопровождении.
